# ESP-IDF Target Documentation Update Guide

Use this guide when updating ESP-IDF documentation for a chip target. The goal is
not merely to make the documentation build: every chip-specific claim must be
traceable to an authoritative source.

## Operating rules

- Identify the target, requested RST file, and peripheral or component before editing.
- Work on one RST file and the target-specific files it directly includes unless the
  user explicitly requests a broader scope.
- Ask for the target TRM and datasheet if they are not available locally.
- If a value cannot be verified, omit it or retain `default="Not updated"` and report
  why. Never invent a plausible value.
- Do not analyze and parse chinese docs (zh_CN/), always do the work on the english docs and
  simply sync the changes to chinese docs afterwards.

## Source hierarchy

Use sources according to the kind of claim being checked.

For hardware facts such as pins, straps, clocks, peripheral counts, channels, and
package options, trust sources in this order:

1. Target TRM and datasheet.
2. Generated target register and pin headers, such as:
   - `components/soc/<target>/register/soc/*_reg.h`
   - `components/soc/<target>/register/soc/*_struct.h`
   - `adc_channel.h`
   - `clk_tree_defs.h`
   - `gpio_sig_map.h`
   - `io_mux_reg.h`
   - `uart_pins.h`
3. `components/soc/<target>/include/soc/soc_caps.h` and
   `components/soc/<target>/include/soc/Kconfig.soc_caps.in`.

During chip bring-up, treat capability files as a list of claims to verify, not as the
primary authority.

Use the relevant driver and HAL implementation to determine whether ESP-IDF exposes a
hardware feature and which API or mode is currently supported. Hardware presence in the
TRM does not prove driver support.

For runtime output such as boot logs, detected chip revision, heap size, and flash size,
a real board is authoritative. Do not manufacture output when no board is available.

If sources disagree, follow the hierarchy above and report the disagreement. Do not
silently change headers, capability definitions, or driver code as part of a
documentation-only task.

## Understand the ESP-Docs target mechanisms

ESP-IDF documentation is built once per `(language, target)` pair from a shared source
tree. Target-specific content is selected through the following mechanisms.

### Target substitutions

Use `{IDF_TARGET_*}` substitutions for a word or value inside otherwise shared text:

```rst
{IDF_TARGET_TX_PIN:default="Not updated", esp32c6="GPIO16"}
```

- Audit every local substitution definition in the requested file. A missing target can
  silently render the default.
- A `default=` value is required.
- Prefer `default="Not updated"` when the target value is unknown.
- Local definitions do not carry into included files. Define a substitution in the
  included file when it is used there.
- Avoid substitutions in alignment-sensitive grid tables because replacement length can
  break the markup.
- Built-in substitutions include `{IDF_TARGET_NAME}`, `{IDF_TARGET_PATH_NAME}`,
  `{IDF_TARGET_CFG_PREFIX}`, toolchain prefixes, and TRM/datasheet URLs.
- A new target may also require support in `esp_docs/constants.py` and
  `esp_docs/esp_extensions/format_esp_target.py`.

### Conditional blocks

Use `.. only:: TAG` for paragraphs, blocks, or sections:

```rst
.. only:: SOC_LP_CORE_SUPPORTED

   This content is available when the target has an LP core.
```

Prefer a verified `SOC_*`, `ESP_ROM_*`, or `CONFIG_*` capability tag over a list of chip
names. Use a target name for genuinely target-specific content such as pin assignments,
strapping behavior, or an erratum.

### Conditional list items

Use `.. list::` when only individual bullets differ:

```rst
.. list::

   - Common item
   :SOC_BT_SUPPORTED: - Bluetooth-specific item
```

The condition syntax supports `and`, `or`, `not`, and parentheses.

### Whole-document filtering

Excluding a document for some targets requires two matching changes:

1. Add the condition to the document's toctree entry.
2. Add the document under the same condition in
   `docs/conf_common.py::conditional_include_dict`.

Changing only one side can produce an orphan-document warning or a broken link.

### Included files

Resolve target-dependent includes such as:

```rst
.. include:: inc/{IDF_TARGET_PATH_NAME}/feature.inc
```

Read the resolved `.inc` file and treat its claims as part of the parent document. Update
it when it contains stale target-specific content.

Distinguish hand-written includes from `.. include-build-file::` content. Build-file
includes are generated by ESP-Docs and should not be edited as source files.

Every new hand-written `.rst` or `.inc` file must have a matching relative path under
both `docs/en/` and `docs/zh_CN/`.

## Workflow

### 1. Inspect the requested document

Read the RST file before editing. Inventory:

- Local `{IDF_TARGET_*:...}` definitions.
- `.. only::` conditions.
- `.. list::` conditions.
- Conditional toctree entries.
- Hard-coded chip names.
- Counts, pins, channels, clocks, formats, limitations, and feature claims.
- Examples and API recommendations.
- `.. include::` and `.. include-build-file::` directives.
- Target-specific TRM or datasheet links.

Resolve and inspect any target-specific hand-written includes.

### 2. Derive checks from the claims

Do not apply a fixed peripheral checklist blindly. For every target-specific claim,
identify its category and check only the relevant sources:

- Pins and signals: TRM IO MUX/GPIO Matrix tables, then `io_mux_reg.h` and
  `gpio_sig_map.h`.
- Counts and channels: TRM peripheral chapters, generated register headers, then
  capability definitions.
- Clocks: TRM clock chapters and `clk_tree_defs.h`.
- Data formats and register behavior: TRM and generated register definitions.
- Feature support: TRM for hardware presence, then driver/HAL implementation for ESP-IDF
  availability.
- Runtime output: connected hardware.
- Target-specific includes: the resolved `.inc` file and every source needed to verify
  its claims.

Use documentation elsewhere in the tree only as a hint, never as the final source of
truth.

### 3. Select the correct target mechanism

- Use a substitution for a value embedded in shared prose.
- Use `.. only::` for a target-dependent block.
- Use `.. list::` for a target-dependent list item.
- Use matching toctree and `conditional_include_dict` conditions for a whole document.
- Use a target-specific `.inc` when content is too different to express clearly with
  conditions.
- Prefer verified capability gates to enumerating chip names.

### 4. Make only verified changes

Update documentation claims only after verification. Keep edits within the requested
scope. If an authoritative source exposes an unrelated code or capability bug, report it
separately rather than expanding the documentation change.

When adding a new target:

- Audit every local substitution in the file.
- Create required per-target includes in both languages.
- Update `docs_not_updated/<target>.txt` according to the ESP-IDF documentation workflow.

### 5. Validate

CI will build and validate the docs, there is no need to do so locally.

### 6. Report

Summarize:

- Files changed.
- Each chip-specific claim changed and the exact source used to verify it, including the
  TRM/datasheet section or source path where useful.
- Claims that could not be verified and what was omitted or left as
  `default="Not updated"`.
- Whether hardware was available for runtime-output verification.
- Any disagreement between the TRM, generated headers, capability definitions, and
  driver implementation.
- Validation commands and their results.

Ask before committing. Documentation for unreleased targets may require the changes to
remain local.
